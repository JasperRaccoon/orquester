## Full retention bar

Each contract below states all six requirements. Test-specific inputs/failure modes are in the disposition table; assertions use fixed fixture values rather than production-derived expected results.

* **E — executor protocol and persisted-chain fallback.** (1) Saved workflow graphs tolerate obsolete agent names; the daemon catalogue controls available chat launchers/accounts, and the direct chat API carries explicit account/model identity. (2) A failed runnable workflow, an unavailable account launch, wrong prompt/wire identity or wrong returned account fails these tests. (3) Expected launcher/account/prompt and skip codes are literal independent inputs/contracts. (4) Observe `AgentExecutor.execute`, returned output and `DaemonApi` session-create requests. (5) No private method names, timing overrides or exact diagnostics are asserted. (6) This is the lowest seam integrating chain selection with live catalogue refusal and actual launch; selector/preview/graph validation cannot own it. Non-test callers: daemon wiring registers the executor in the workflow engine.
* **F — quota reset ownership.** (1) Workflow cooldown persistence and provider quota isolation require a managed account to use its own reset, and accountless providers to use their own backoff. (2) Wrong provider key/reset delays an unrelated runnable agent or retries a limited provider too early. (3) Literal distinct account resets and one-/two-hour durations are independently chosen. (4) `coolDown` is the executor's stable policy boundary; observe stored cooldown records. (5) No private collaborator call shape or generated prose is asserted. (6) Storage tests prove persistence/expiry, while this owner alone chooses the quota/reset. Non-test caller: executor failover.
* **K — persisted cooldown keys.** (1) Persisted cooldown keys identify native family/account and accountless provider; stable keys are a storage compatibility contract. (2) Changed keys lose active limits across daemon restarts or combine unrelated provider limits. (3) Literal historical keys are independent of the key builder. (4) The cooldown subject/key boundary is used by selection and failover. (5) Identifier-only and internal refactors preserve these external bytes. (6) This lowest key owner covers native/system/provider boundaries without replaying full execution. Non-test callers: select, failover and executor.
* **W — session-create wire payload.** (1) The direct chat API requires explicit account choice, workflow owner, full-access policy and model selection in its chat selection field. (2) A malformed request starts the wrong model/account, loses workflow ownership or blocks unattended work. (3) Expected wire keys/values come from the API contract and fixed request inputs. (4) The request-body builder is the lowest seam producing this public API payload. (5) Assertions tolerate internal decomposition and omit presentation text. (6) The retained executor happy path covers a real launch; the builder test alone exercises explicit system-account/model-options placement combinations. Non-test caller: executor's session creation.
* **S — candidate quota isolation.** (1) Provider-specific accountless limits must not suppress another provider or native system login. (2) The wrong candidate set prevents usable fallback or reuses a limited provider. (3) Fixed cooldown keys and explicit chain entries provide an independent expected candidate set. (4) `selectAccount` returns the candidate selection used by execution/preview. (5) No comparator implementation, private callback or exact explanation is observed. (6) Lowest selection seam owns this matrix; execution coverage uses different fallback failures. Non-test callers: executor failover and account preview.
* **V — catalogue readiness.** (1) Validation may reject unknown models only once the provider's catalogue has been probed. (2) Treating an unprobed list as authoritative incorrectly rejects valid workflows; ignoring a ready list accepts nonexistent models. (3) Explicit provider status and literal model arrays give independent expected normalized data. (4) `toValidationCatalog` is the stable provider-to-graph-validation adapter. (5) No source inspection or private callback shape is used. (6) Graph validation receives its normalized result and cannot cover provider readiness conversion. Non-test caller: daemon workflow validation wiring.
